## Context

Collaborators (Slack thread with Gregory Wagner, Valentin Churavy) and funders
(NSF PI meeting, legoESM authors) keep asking why the project uses Julia+Enzyme
instead of JAX. The honest answer is narrower than "JAX can't sort": Enzyme
differentiates the *imperative* program, so algorithms whose efficient form is
irregular — data-dependent shape, data-dependent control flow, sequential
in-place update — keep their efficient form under reverse-mode AD. In JAX they
must be regularised (padding, masks, static trip counts, implicit
differentiation) and sometimes pay for it. Many JAX users assume the things JAX
can't do are not differentiable at all.

Deliverable: a GitHub Pages site (Quarto) with one page per example, each showing
an **Enzyme.jl**, **Reactant.jl** and **JAX** implementation side by side, a
cross-implementation gradient correctness check, and CPU/GPU timings + memory,
generated by notebooks that anyone can clone and re-run on a CUDA GPU. Reactant
is the third column on purpose: it is Julia with the XLA/static-graph model, so
it isolates "Enzyme on LLVM" from "Julia syntax" as the source of the advantage.

Decisions already made: Quarto; all four examples; repo at `michel2323/WEANJ`
first, transfer to `EnzymeAD` after review; JAX side is idiomatic best-effort
(JAX-MD / Diffrax / Optimistix patterns, documented honestly, including where JAX
wins); Reactant included.

Verified environment (2026-10-14): RTX 5000 Ada 16 GB, driver CUDA 13.0; Julia
1.12.5 (juliaup); Python 3.12/3.14 via `uv`; `gh` logged in as michel2323.
Enzyme.jl 0.13.216 / Reactant.jl 0.2.293 / CUDA.jl 6.4.2 / KernelAbstractions
0.10 all support Julia 1.12 (Enzyme CI tests 1.10–1.13). JAX 0.11.2 ships
`cuda13` wheels for py3.12 and 3.14; `jax-md 0.2.29` resolves. Quarto 1.10.19 is
current.

## Architecture

### Quarto constraint and how we handle it

One `.qmd` = one engine. Each example therefore has three *source notebooks*
(one per implementation) and one *host page* that embeds their cells:

```
examples/01-particles/
  index.qmd      # host page: prose, math, tabsets with {{< embed enzyme.qmd#loss echo=true >}} etc.
  enzyme.qmd     # engine: julia      (native Quarto engine, QuartoNotebookRunner; no IJulia)
  reactant.qmd   # engine: julia
  jax.qmd        # engine: jupyter, kernel from the uv venv (QUARTO_PYTHON)
```

Tabsets use `{.panel-tabset group="impl"}` so choosing "JAX" on one tabset
switches all tabsets on the page. Julia notebooks pin the toolchain in frontmatter: `julia: exeflags: ["+1.12", "--project=<rel>/julia"]` (requires juliaup channel `1.12`; manifest resolved with 1.12.7). The Python interpreter is set per machine in the gitignored `_environment.local` (`QUARTO_PYTHON=<abs>/python/.venv/bin/python`).
`execute: freeze: true` project-wide:
notebooks run locally on the GPU, `_freeze/` is committed, GitHub Actions only
renders HTML (no Julia/CUDA on the runner).

### Shared protocol (encoded in helpers, documented in methodology.qmd)

- Inputs: generated once in Julia with fixed seeds, written to `data/*.npz`;
  every implementation loads the same arrays.
- Correctness: every notebook computes the gradient at the same point and writes
  it to `benchmarks/results`; the host page asserts all three agree (Float64,
  rtol 1e-8) and agree with central finite differences on a few components.
  This is the credibility step — the table shows *the same gradient* from three
  tools.
- Timing: **Float64 everywhere** (user decision 2026-10-14, after Enzyme GPU Float32
  runtime-activity errors): timing and correctness runs use the same precision.
  Consumer GPUs have low FP64 throughput; stated on the methodology page. Warm-up excluded; compile time reported separately (matters for
  Reactant and JAX); median of k runs; GPU synchronised (`CUDA.@sync`,
  `block_until_ready()`); N sweep (e.g. 1e3…1e6) → log-log scaling plot.
  Memory: peak device memory (`CUDA.memory_status`/`CUDA.@allocated`; JAX
  `compiled.memory_analysis()` + `device_memory_stats`).
- JAX fairness: `jit`, buffer donation, `jax.checkpoint` where a practitioner
  would use it, library implementations (jax-md `cell_list`/`neighbor_list`,
  Optimistix for implicit diff, Diffrax for adaptive stepping). Each page has a
  "Where JAX wins / what we did not do" callout.
- Results JSON schema:
  `{example, impl, device, dtype, N, forward_s, grad_s, compile_s, peak_mem_bytes, grad_checksum}`.

## Examples

1. **Particles / cell-list SPH loss** (the Slack trigger; data-dependent shape + loops)
   N particles in a periodic 2D box, cubic-spline kernel,
   ρ_i = Σ_j m W(|x_i−x_j|,h), loss = Σ_i (ρ_i − ρ_target)², gradient w.r.t. positions.
   - Enzyme: counting sort by cell id (`sortperm!` or hand-rolled, in-place SoA
     permute), cell offset array, loop over 9 neighbour cells with dynamic
     ranges. CPU loops + KernelAbstractions kernel for GPU.
   - Reactant: `sortperm` lowered to stablehlo sort, but neighbour ranges must
     be static → padded cell list (same regularisation as JAX; shows it is the
     execution model, not the language).
   - JAX: jax-md `cell_list` + `neighbor_list` with `did_buffer_overflow`
     rebuild loop, or hand-written padded cell list + `segment_sum` if jax-md
     has bit-rotted against jax 0.11.
2. **Sequential in-place sweep** (Gauss–Seidel for 2D Poisson; sequential dependency)
   Loss = ‖u_K(θ) − u_obs‖², θ = source term, K lexicographic GS sweeps.
   - Enzyme: in-place sweeps, reverse through the loop; memory vs K measured.
   - JAX: (a) same algorithm as `lax.scan` over rows with the full array as
     carry — sequential on GPU, O(K·N) residuals without `checkpoint`;
     (b) idiomatic red-black GS (parallel) — the reformulation practitioners
     actually use, reported as the fair JAX number.
   - Reactant: `@trace for` loop with array carry; same model as JAX.
3. **Compaction / filtering + scatter-add** (data-dependent output size)
   Over T steps: select particles inside a moving region (`x[mask]` / `push!`,
   data-dependent count M), deposit with linear (CIC) weights into a histogram
   (`hist[j] += w`, data-dependent j), loss = ‖hist − target‖².
   - Enzyme: `filter!`/`push!` into growing buffer, scalar scatter-add; GPU via
     KA kernel with atomics.
   - JAX: static capacity + mask, `.at[].add` / `segment_sum`, overflow guard
     outside jit.
   - Reactant: static shapes, masked.
4. **Adaptive / convergence-tested solver** (data-dependent control flow)
   Newton solve of F(u,θ)=0 to tolerance, loss g(u*(θ)). Stretch: adaptive RK45.
   - Enzyme: differentiate the `while` loop directly; also an implicit-function
     rule as the "right" alternative, to be even-handed.
   - JAX: show `jax.grad` through `lax.while_loop` failing (captured error),
     `fori_loop` with fixed count, `optimistix.root_find` (implicit diff);
     Diffrax for the RK stretch.
   - Reactant: `@trace while` — measure whether reverse mode through it works;
     report honestly either way.

## Verification
- Each source notebook ends with assertions: gradient matches FD, and (on the
  host page) all three implementations' gradient checksums match within
  tolerance; a failing assertion fails `quarto render`.
- `make run-gpu`: refuses unless the GPU is idle (`make gpu-check`), re-executes every
  source notebook (rendering a single file ignores freeze), then renders the site.
  A reduced-size CPU `make check` is still to be designed (Phase 2).
- `quarto render` locally after `run-gpu` must produce the site with GPU
  numbers; then `git commit _freeze benchmarks` and a GitHub Actions run must
  render identically without executing anything.
- Fresh-clone test of `setup.qmd` instructions on this machine.
- Cross-check numbers for sanity against published references (JAX-MD
  cell-list overhead, Enzyme SPH examples) before publishing.
